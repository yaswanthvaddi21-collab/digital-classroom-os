# 0013 — Document and diagram integration in Phase 6: document schema 3 from a frozen Phase 5 vocabulary, new diagram attributes, off-screen previews and editable data in PNG previews

**Status:** Accepted in Phase 6. Round 1 laid the foundation (decisions 1 to 6); Round 2 (DIALOG, NODE, CLIPBOARD, EXPORT) and Round 3 (integration) built on it at the `// @phase6:<area>` markers (decisions 7 to 12).

## Context

Phase 6 integrates Diagram Studio into Document Studio: diagrams embedded in documents gain alignment, a caption, alternative text and a vector preview; missing previews must be redrawn from the diagram's own data; copy and paste must cross between the two studios; and exports must keep diagrams editable where the format allows. Each of these changes what a stored document can contain.

Saved documents were schema 1 or 2 ([ADR 0011](0011-document-format-phase4.md)). The Phase 4 and Phase 5 builds (git `206e080`, `8f772ba`) read schema 2 and open anything above it read-only. Their editor schema silently drops node attributes it does not know (ProseMirror keeps only declared attributes), and their safety check (`validateDoc`) only refuses unknown attributes that hold a value. A Phase 6 attribute stored in a schema-2 document would therefore be dropped without warning the next time a Phase 5 build saved it (audit `backups/phase6-audit-20261114.md`, "Document compat cannot express new diagram-node attributes"). The owner's rules apply: no destructive migrations, existing documents and diagrams stay compatible, nothing is dropped silently.

The embedded diagram's editable data (`source`) and its rendered PNG preview (`previewId`, a content-addressed attachment, [ADR 0008](0008-attachments.md)) are already stored separately. The preview is made only by the edit dialog, so a lost attachment could be recovered only by opening and saving the diagram again, and every export writes a flat picture.

## Decision

1. **Document schema 3 is decided by a frozen Phase 5 vocabulary.** `packages/document-studio/src/compat.ts` holds `V020_VOCABULARY`, generated from the `8f772ba` editor schema: every node and mark type with each attribute's default (the `diagram` node with its seven attributes `source previewId naturalWidth naturalHeight width height title`), the content fields (`schemaVersion doc page mode comments language`), the editing modes, the page fields, sizes, orientations and margins, and the closed value sets of `columns`, `pageNumberFormat`, `pageNumberAlign` and `pageNumberText`. It contains all of `V010_VOCABULARY` and is never edited. `docNovelty` and `contentNovelty` take the vocabulary to measure against (v0.1.0's by default). `schemaFor` and `contentSchemaFor` return 1 when content uses only v0.1.0's vocabulary, 2 when it uses only the Phase 5 vocabulary, and 3 otherwise: a new node or mark type, a new attribute holding something other than its default, a new content or page field with a value, or a page value outside a frozen choice. `DOCUMENT_SCHEMA` is 3, with an identity upgrader 2 → 3. Every save goes through `contentSchemaFor` (`DocumentEditor` `compose`, `importedContent`), so the number follows the content: a document that uses nothing new stays schema 2 and the Phase 4 and Phase 5 builds keep editing it; one that uses a Phase 6 attribute is schema 3 and those builds open it read-only (protected view), so they can never save it without the attribute. Removing the last Phase 6 value makes the document schema 2 again. A later feature makes documents schema 3 without touching `compat.ts`.

2. **New diagram attributes, all `null` by default.**

   | Attribute | Meaning | Valid values | Clipboard HTML |
   |---|---|---|---|
   | `align` | Alignment on the page (`diagramAlign`: centre when null, as before) | `left`, `center`, `right` | `data-align` |
   | `caption` | Caption shown below the diagram (`diagramCaption`) | text | `data-caption` |
   | `alt` | Alternative text; the title is used when null (`diagramAltText`) | text | `data-alt`, and the figure's `aria-label` |
   | `svgPreviewId` | Attachment id of a vector (SVG) preview of the same drawing | an attachment id | `data-svg-preview-id` |

   The editor writes every attribute, so a diagram saved by this build stores the four keys as `null`. That keeps it schema 2, and the Phase 4 and Phase 5 schemas read it without losing anything (they drop only the null keys; `compat.test.ts` rebuilds that schema to check). Copy and paste carry the attributes in the `data-diagram` JSON (`toCopy`) only when set, so the clipboard form of every other diagram is byte for byte what it was; `parseHTML` reads the JSON first and the `data-*` attribute second, and an unusable value gives `null`. An edit that returns no new `svgPreviewId` clears the old one (node view and ribbon), so a drawing of the old diagram is never shown or exported. The ODT exporter lists the attributes in `ODT_HANDLED_ATTRS` and writes them all (`diagramBlock` in `export/odt/images.ts`: alignment and caption through the picture paths, alt text as the frame's `svg:desc`, the SVG before the PNG; decision 11). `DIAGRAM_PHASE6_ATTRS` names them, and `compat.test.ts` checks that the build's schema is the frozen vocabulary plus exactly these.

3. **`DiagramHost.renderPreview(source, title?)` draws a diagram off screen.** It resolves `{ png, svg, width, height }` (natural size in CSS pixels; the PNG at 2x, lowered for very large diagrams by `cappedPixelRatio`), or `null` when there is nothing to draw (no data, no visible shapes), and rejects only when the browser cannot draw the picture, so callers can report that. It is optional on the interface, so hosts without a renderer still type-check and callers keep today's placeholder. The app implements it in `apps/web/src/components/DiagramDialogs.tsx` with diagram-studio's new `renderDiagramPreview` (`packages/diagram-studio/src/preview.ts`), which uses the Phase 5 vector renderer: the content the editor would hold for the source (`deserializeDiagram` then `serializeDiagram`), drawn by `renderDiagramPng` (the edit dialog's PNG path) and `renderScene` (SVG), with no editor mounted. The source is only read: a diagram from a newer version is drawn as far as this version can (read-only, as the editor opens it), and nothing is migrated, stored or handed back. The caller stores the result if it needs to: the node view stores a redrawn missing preview with `storePreview` and a non-history attribute update (decision 8); the exports use the drawing without storing it (decisions 11 and 12).

4. **Editable diagram data travels inside the PNG preview.** `packages/document-studio/src/export/diagramPng.ts` has pure functions on bytes. `embedDiagramInPng(png, envelope, { pixelRatio })` returns a copy with a zlib-compressed iTXt chunk, keyword `dcos-diagram`, holding the `.dcosdiagram` envelope of diagram-studio `native.ts` (`{ format: 'dcos-diagram', version: 1, app, title, diagram }`; document-studio does not depend on diagram-studio, so `diagramPngEnvelope` builds the same object and an integration test checks the constants and that `parseNativeFile` accepts it). It also writes a `pHYs` chunk (192 dpi for a 2x preview) so other apps show the picture at its size. Both are placed after `IHDR`, before the image data; an earlier `dcos-diagram` chunk and `pHYs` are replaced; the image data and other chunks are unchanged. `readDiagramFromPng(png)` returns `{ text, envelope }` or `null` and never throws: a missing chunk, a bad CRC, unknown compression, damaged zlib data, text that is not UTF-8 JSON, JSON that is not an envelope, or data past the 64 MB limit (checked while inflating, which is fed 4 KB at a time, so a small "zip bomb" chunk stops a few megabytes past the limit instead of inflating in full) is ignored. The envelope's diagram is not validated there: callers pass `text` to `parseNativeFile`, which checks it strictly and refuses newer versions. This is how diagrams.net makes editable PNGs; the audit's probe showed a custom chunk survives the app's own DOCX and ODT export and re-import.

5. **Round 2 hooks in at markers.** `// @phase6:DIALOG` (dialog draft recovery, unload warning, errors inside the dialog, focus, toasts above the modal, the recovery offer on the editor page), `// @phase6:NODE` (node view sizing and resizing, keyboard opening, caption and alignment display and ribbon fields, missing-preview regeneration, insertion point, content CSS), `// @phase6:CLIPBOARD` (document paste plugins, clipboard text and picture for other apps, Diagram Studio's paste and copy paths) and `// @phase6:EXPORT` (DOCX and ODT exporters and importers, the text and print exports, report notes, the `.dcosdoc` file and the import wiring) marked where each group changes files outside its own. Rounds 2 and 3 replaced most of them with their code; the `DIALOG`, `NODE` and `CLIPBOARD` markers left in `diagramEmbed.tsx`, `extensions/index.ts`, `EditorPage.tsx` and `storage.ts` now describe what is there, and no `EXPORT` marker remains.

6. **Backups.** `MAX_CONTENT_SCHEMA_BY_KIND.document` is 3, so a backup holding a schema-3 document is accepted by this build; the backup's own `schemaVersion` is the highest content schema in it, as before ([ADR 0007](0007-backup-format.md)). Embedded diagram sources are not counted in that number: a schema-2 document may embed a schema-3 diagram, and the Phase 4 and Phase 5 builds keep it byte for byte and open it read-only in their diagram editor (audit, core-storage-recovery), so nothing is lost and counting it would only refuse backups those builds can restore.

7. **Unsaved dialog edits are kept as drafts of their document until they are in it (DIALOG, Round 3).** While the edit dialog has changes it warns before the page unloads, keeps a draft a second after the last change (session `diagram-dialog:<uuid>`, kind `document`, stored as a valid content-schema-2 document holding a note (`DIAGRAM_DIALOG_DRAFT_NOTE`), the diagram as it was when the dialog opened (when it was opened on one) and the edited diagram, so a build before Phase 6, which offers every draft of a document as unsaved document changes, recovers it as an editable "(recovered)" copy showing both instead of an empty document; with a synchronous `localStorage` copy on `pagehide`, when the tab is hidden and on unmount), and holds a Web Lock so other tabs do not offer a draft whose dialog is still open (`apps/web/src/lib/storage.ts`). The editor page offers kept drafts ("Recover diagram edits", "Discard" after a confirmation, "Later"); a recovered edit replaces the diagram it was opened on (same `previewId` and `source`), or is added at the end when that diagram is gone (`apps/web/src/lib/diagramRecovery.ts`). Round 3 closed the last gap: Save no longer removes the draft. It writes the saved diagram into the draft, and the new optional **`DiagramHost.settle(diagram, applied)`**, which Document Studio calls after it tried to put an edit or insert into the document (`openDiagramEditor`, `useDiagramInsert`), removes the draft only when `applied` is true. When the document was reloaded or the diagram removed while the dialog was open (`RELOADED_NOT_APPLIED`, `DIAGRAM_GONE`, `RELOADED_NOT_INSERTED`), or a new diagram could not be placed (`DIAGRAM_NOT_PLACED`), the draft stays and the offer is shown again at once. The offer reads the draft again before reopening it, so a draft recovered or discarded in another tab is not applied twice. Toasts follow the top modal dialog (`packages/ui/src/toast.tsx`, RG-8); save errors are shown inside the dialog.

8. **The node view (NODE).** A diagram is a `<figure class="dcos-diagram">` sized by `width` plus `aspect-ratio` (never a fixed height), aligned by `data-align`, with a `<figcaption>`. Resizing uses pointer capture, ends without a change on `pointercancel` or a lost capture, and starts from the width on screen. `openDiagramEditor` is the one way to open the editor (double-click, double-tap, Enter, F2, the ribbon and the object bar), with the same guards. The "Selected diagram" object bar sets alignment, caption, alternative text and the title; in Round 3 its text fields commit to the diagram they were typed for, even when another diagram is clicked before they lose focus. A missing preview is drawn again from `source` with `renderPreview`, stored with the new optional `DiagramHost.storePreview` and set without an undo step; this is the only place in the editor that redraws and stores a preview (exports draw without storing, decision 11; Round 3 removed the clipboard plugin's second redraw of pasted diagrams).

9. **Sizes never depend on the window (CLIPBOARD, NODE, Round 3).** `diagramRoomAt(view, pos, textWidth)` gives the widest a diagram may be stored at a position: nothing narrower than the page at the top level, and inside a table cell, list item or text box that container's share of the editor's width applied to the page's text width. Paste, drop, shapes pasted from Diagram Studio and the ribbon's Insert use it. A copy and paste on a phone therefore stores the same size as on a desktop; CSS fits the picture to a narrower window. Sizes read from pasted data and from DOCX/ODT pictures are bounded (`boundDiagramSize`).

10. **The clipboard (CLIPBOARD).** Shapes copied in Diagram Studio paste into a document as a new embedded diagram through the new optional `DiagramHost.diagramFromShapes` (never as JSON text); an embedded diagram pasted into Diagram Studio becomes its shapes, and a newer schema is refused with the existing message. Diagram Studio writes readable labels as `text/plain`, its JSON in `application/x-dcos-diagram` and inside its HTML. Copying a diagram gives other apps `[Diagram: title]` and an `<img>` of the preview (with the caption), read ahead into data URLs for selections the user makes. After a pasted diagram the cursor moves past it, so a second Ctrl+V adds another copy.

11. **Exports (EXPORT).** DOCX and ODT write each diagram's PNG with its `.dcosdiagram` envelope (decision 4) and a pHYs density from the PNG's pixels per CSS pixel, unrounded since Round 3 so a large diagram's natural size survives exactly; importing such a picture gives an editable diagram again, with its alignment, caption and alt text and the size Word shows (`wp:extent`). DOCX writes SVG with a PNG fallback (`asvg:svgBlip`), ODT a frame with an SVG then a PNG `draw:image`, and print uses the SVG. A missing preview is drawn from the data at export; one failing preview never aborts an export. The native per-document file `.dcosdoc` (JSON: content plus the pictures it refers to) is exported from the Export menu and imported through "Import document" and "Import a file"; its import is strict about schemas, and every picture id the file names is replaced by the stored copy's id or null (Round 3: also when none of its pictures can be read). Round 3 made the DOCX size marking read single-quoted attributes and a raw `>` in attribute values (such files could not be imported at all), and gives a picture cropped or stretched in Word its own proportions.

12. **No SVG preview is stored at save time.** The dialog stores only the PNG; `svgPreviewId` stays null, and DOCX, ODT and print draw the SVG from the source with `renderPreview` when they need it. Storing it would make every document with a newly saved diagram content schema 3 and read-only in the Phase 4 and Phase 5 builds, for a drawing that can be made again from the data at any time. `svgPreviewId` is kept, copied, backed up and exported when a document has one (`.dcosdoc` files can carry it).

## Consequences

- Documents that use no Phase 6 feature stay schema 2 (and v0.1.0 content stays schema 1); the v0.1.0 fixtures, the upgrade test and every earlier golden are unchanged and at their schema.
- Stored diagram nodes gain four `null` keys on their next save. No earlier build is affected (they ignore null unknown attributes), but tests that compared diagram attributes exactly now include them.
- The first Phase 6 attribute a user sets makes the document read-only in the Phase 4 and Phase 5 builds, with their usual "saved by a newer version" notice.
- A missing preview can be redrawn from the data without the editor on screen; the node view (pasted diagrams included) and the exports use it.
- Exported PNG previews can carry the full editable diagram, which makes those files larger by the compressed size of the diagram (typically a few kilobytes).
- `DiagramHost` gained four optional methods (`renderPreview`, `storePreview`, `diagramFromShapes`, `settle`); the existing ones are unchanged, and a host without the new ones keeps the Phase 5 behaviour.
- A host that sets `settle` must expect it for every non-null result of `edit()`; the app keeps a dialog's draft until then.
- DOCX, ODT and print draw one SVG per distinct diagram at export time (decision 12).

## Verification

- `packages/document-studio/src/compat.test.ts`: `V020_VOCABULARY` is supported with the same defaults, equals this build's schema minus exactly the Phase 6 diagram attributes, contains all of v0.1.0, and knows every Phase 5 page field; diagrams with only Phase 5 attributes (or Phase 6 ones at null, as the editor writes them) stay schema 2; each Phase 6 attribute, anywhere in the tree, gives schema 3; page values outside the frozen choices and new fields give schema 3; v0.1.0 fixtures and backup stay 1; schema 3 opens editable here, 2 → 3 changes nothing but the number, 4 is refused as newer; a Phase 5 schema reads an unchanged diagram written by this build without loss.
- `packages/document-studio/src/extensions/extensions.test.ts`: the new attributes survive copy, cut and paste; the clipboard form of a diagram without them is exactly as before; `data-*` fallbacks and unusable values.
- `packages/document-studio/src/DocumentEditor.test.tsx`: an edit keeps alignment, caption and alt text and clears the old SVG preview id (fails without the fix).
- `packages/document-studio/src/export/diagramPng.test.ts`: round trip, chunk order and CRCs, compression, pHYs at 192 dpi, replacement, refusals on write, and every damaged or oversized case on read.
